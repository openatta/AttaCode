# TUI↔Core 粘合层 需求规格

**目标：** 让用户在 AttaCode TUI 的输入区提交自由文本后，粘合层将其转发给 AttaCore 引擎处理，并把引擎返回的各类信息按类别实时渲染到 TUI 对应区域（以转录区为主），形成可交付给客户使用的编程助手交互闭环。

**背景：** AttaCode 定位为"AttaCore 引擎的终端 UI 前端"，本身不含引擎逻辑（见 CLAUDE.md）。本次从零设计 TUI 与 Core 之间的粘合层，作为 TUI 编程场景的核心交互路径。Core 仓库中已有面向消费者的参考实现（demo 实现、daemon 所用的 crate 接口），将作为后续架构设计阶段的接口参考来源；本文档只界定"要做什么"，不涉及具体接口/crate/数据结构。展示分类维度参考 Codex CLI、OpenCode 等同类编程助手 TUI 的信息呈现范式。

## 范围

- In scope:
  - 用户在 TUI 输入区提交文本 → 粘合层调用 Core 侧对应能力 → 获得处理结果的完整交互闭环
  - Core 返回信息流的分类识别与路由：按类别分发到 TUI 的不同展示形式/区域
  - 转录区中，每一次工具调用（请求参数 + 执行结果）作为独立可辨识的展示单元
  - 需要用户确认的操作（权限请求）在 TUI 内的交互式确认流程，及决定回传给 Core
  - 异常/失败信息的呈现，且不中断整体交互流程
  - 覆盖"客户交付"要求的信息类别，具体包括：
    - 用户输入回显
    - Assistant 文本回复（流式）
    - 工具调用请求与结果（含不同工具类型的结果内容，如文件变更、命令输出、搜索/查询结果等）
    - 权限确认请求
    - 错误/异常
    - 用量与统计信息（如 token 用量、耗时等元信息）——展示为常驻区域（如状态栏），而非转录区内的普通条目
    - 会话/生命周期状态事件（如会话开始/结束、模型切换等）
  - 新输入在 Core 处理当前轮次期间的排队机制（不打断、不拒绝，按序处理）
  - 转录区中早前轮次工具调用记录的可回溯查看能力
- Out of scope:
  - Core 侧引擎能力本身的修改（AttaCore 是独立 submodule，见 CLAUDE.md"AttaCore 补丁"章节，需求不涉及）
  - 具体 crate/trait/数据结构/接口签名设计（属于架构设计阶段）
  - 键盘快捷键/slash 命令系统的规则细节（已有既定系统，仅作为触达粘合层的输入来源之一）
  - 非 TUI 交付形态（如 headless CLI、Web UI）——已在 CLAUDE.md 中明确移除出 scope
- 前置依赖：
  - Core 侧存在可供参考的 demo/daemon 接口形态，作为架构设计阶段的分析对象（本阶段不读取，仅确认其存在并作为后续输入）
  - TUI 现有的输入/渲染框架（转录区、状态栏等）已具备承载分类展示的基础界面结构

## 非功能需求

- **稳定性基准：** 交互体验（响应及时性、异常恢复能力、长会话下的可靠性）以 Claude Code 为对标基准，不应出现因单次工具失败或异常输出导致整个 TUI 卡死/崩溃的情况。

## 用户场景

### 场景 1：纯文本问答（正常流程）
- 给定：用户在 TUI 输入区输入一段不需要工具协助的问题
- 当：用户提交该文本
- 则：粘合层将文本转发给 Core，Core 返回的 assistant 文本流式呈现在转录区，用户可见渐进式生成的回复

### 场景 2：需要工具协助的请求（正常流程）
- 给定：用户输入的请求需要 Core 调用工具（如读取文件、执行搜索）才能完成
- 当：Core 在处理过程中发起一次或多次工具调用
- 则：转录区为每次工具调用生成独立的展示单元，包含调用的意图/参数摘要与执行结果，用户能清楚区分"模型在说话"与"模型在调用工具"

### 场景 3：需要用户授权的操作（正常流程，含交互）
- 给定：Core 触发的工具调用属于需要用户确认的高风险操作（如写文件、执行命令）
- 当：Core 发出权限确认请求
- 则：TUI 呈现明确的确认交互，用户做出允许/拒绝（或记住选择）的决定后，该决定被回传给 Core，Core 据此继续或中止该工具调用；在用户做出决定前，交互流程应清晰指示"等待用户确认"的状态

### 场景 4：工具执行失败或连接异常（异常流程）
- 给定：Core 侧某次工具调用执行失败，或 Core 与粘合层之间的通信中断
- 当：粘合层捕获到该失败/异常
- 则：转录区以明确可辨识的方式呈现错误信息，且不导致 TUI 无响应或崩溃，用户仍可继续后续输入或采取恢复操作

### 场景 5：用户在 Core 仍在输出时提交新输入（边界条件）
- 给定：Core 尚未完成当前一轮回复（仍在流式输出或执行工具调用）
- 当：用户在此时提交新的文本
- 则：新输入进入排队等待，待当前轮次结束后按提交顺序依次处理，不打断正在进行的轮次，不拒绝用户输入

### 场景 6：单次工具调用产生大量输出（边界条件）
- 给定：某次工具调用返回的内容体量很大（如大文件内容、长命令输出）
- 当：该结果需要在转录区展示
- 则：该展示单元默认以折叠形式呈现（仅展示摘要/首尾片段等），用户可主动展开查看完整内容

### 场景 7：查看早前轮次的工具调用详情（正常流程）
- 给定：会话已进行多轮，转录区中存在早前轮次的工具调用记录
- 当：用户希望回顾非最新一轮的工具调用详情
- 则：用户可以在转录区中定位并查看早前轮次的工具调用请求与结果，不局限于仅能查看最新一轮

## 待澄清

- [ ] "客户交付"验收标准已明确以 Claude Code 的稳定性体验为基准；具体是否有独立于此基准之外的客户场景或交付时间节点，仍可在后续阶段按需补充。

## 风险

- 需求来源提到参考 Core 的 demo/daemon 接口与 Codex/OpenCode 的 TUI 范式，但两者的具体信息分类粒度可能不完全一致；若架构设计阶段发现 Core 实际暴露的信息类别少于本文档列出的类别，需要回到本文档调整范围，而非在架构阶段静默裁剪需求。
- "从零设计"的定位与仓库当前已存在的 TUI↔Core 集成（CLAUDE.md 中描述的数据流）之间可能产生认知落差，如果后续设计发现两者无法完全独立，需要及时与现有实现的边界做一次澄清，避免重复实现或需求与现状脱节。
- 场景 5、6 的待澄清项若不及早确定，可能导致架构设计阶段基于错误假设展开（如假设允许打断，实际需要排队），造成返工。
